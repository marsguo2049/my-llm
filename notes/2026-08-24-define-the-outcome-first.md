# 先定义结果，再决定要做什么

**日期：2026-08-24**

今天，我原本准备把一个 Python 实现的 GVNS 翻译成 C++，目标是提高运行速度。受之前 Hybrid GA 项目的影响，我下意识地认为：既然要迁移算法，就连优化模型也要一起翻译。

导师提醒我：这次真正需要加速的只是 GVNS，并不需要重写模型。

我才意识到，自己把“以前项目的做法”误当成了“当前任务的必要步骤”。问题不在于大模型让我混乱，而在于我没有先把最终目标说清楚，也没有从第一性原理判断：为了得到这个结果，哪些工作是必需的？

即使是 Hybrid 算法，也不一定需要把所有建模代码迁移到 C++。只要接口合适，Python 可以导出 LP/MPS 文件，再由 C++ 和求解器读取；也可以只迁移真正影响性能的算法部分。是否需要这样做，应由目标、调用方式和性能瓶颈决定，而不是由“技术栈必须统一”的直觉决定。

## 给自己的人机协作检查表

在让大模型开始写代码前，先回答四个问题：

1. 我最终想得到什么可验证的结果？
2. 达到这个结果，最少需要改变什么？
3. 哪些现有部分可以直接保留或复用？
4. 如何用一个小实验验证这条路线？

然后先让大模型审查路线，而不是立刻生成实现：

> 我的最终目标是……  
> 当前系统是……  
> 我计划做……  
> 请从第一性原理分析：哪些步骤是必要的，哪些可能是无用功？请给出满足目标的最小实现路径和验证方法。

这次教训可以概括为一句话：

> **先定义结果，再拆解必要条件；先让 LLM 帮我审路，再让它帮我赶路。**

第一性原理帮助我找到真正必要的工作，二八法则帮助我优先完成最有价值的部分。对人机协作来说，清楚地定义目标，往往比更快地生成代码更重要。
