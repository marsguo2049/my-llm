# 不要重复阅读整个项目：让 LLM 只汇报变化

**日期：2026-08-25**

大模型经常把“完整”理解为“尽可能详细”。但在人机协作中，过多输出也会成为负担。

我曾让大模型审查算法开发，它一度返回约三万字。原本只想解决一个问题，最后却需要重新判断大量已经看过或暂时不重要的内容，整个人陷入了信息漩涡。

问题不只是回答太长，而是输出没有保存审查状态。每一轮都像重新介绍整个项目，而不是告诉我：这次发生了什么变化，还有什么需要决定？

## 从长篇回答变成决策账本

算法开发通常有相对固定的流程，因此可以维护一份持续更新的报告：

1. **当前摘要**：目标、当前进展和下一步，控制在一屏内。
2. **待审查事项**：只展示新增、发生变化或尚未决定的内容。
3. **已处理记录**：默认折叠，需要时再展开查看。

每个审查项使用四种状态：

- **Pass**：已经审查并接受，默认隐藏。
- **Reject**：不接受，需要修改、替换或删除。
- **Uncertain**：证据不足或尚未理解，需要进一步验证。
- **Comment**：已有具体意见或问题，等待回应和处理。

每项还应保留编号、依据、评论、更新时间和依赖关系。这样，大模型下一轮不必重新生成完整报告，只需更新受影响的项目。

## 用 HTML 承载审查过程

相比静态文本，HTML 可以把输出变成一个简单的审查界面：

- 为每项提供 **Pass / Reject / Uncertain / Comment** 操作；
- 默认隐藏已经 Pass 的内容；
- 按状态筛选，只查看当前需要处理的项目；
- 保存评论和历史变化；
- 导出 Markdown，形成可追踪的开发报告。

但“已经 Pass”不代表永久正确。如果目标、输入、假设或上游模块发生变化，所有受影响的项目都应自动重新打开，进入 **Uncertain** 状态。

这套方法的核心是：

> **不要让 LLM 每次重新解释整个项目，而要让它维护项目状态，只汇报变化和待决事项。**

大模型的价值不只是生成更多内容，也应该帮助我们减少重复阅读，把注意力留给真正需要判断的地方。
